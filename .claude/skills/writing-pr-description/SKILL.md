# PR 説明の作成・更新

レビュワーがサクッと読んで変更意図を理解できる PR 説明を書く。

**基本原則:** 「何を変えたか」より「なぜ変えたか・何が変わるか」を優先する。冗長にしない。

## プロセス

### ステップ1: 変更内容の把握

```bash
# 現在のブランチの PR を確認（既存 PR の更新の場合）
gh pr view --json number,title,body,headRefName,baseRefName

# ベースブランチとの差分を取得
gh pr diff <number>
# または
git diff origin/<base>...HEAD
```

変更ファイルの一覧と diff を読み、以下を整理する:
- **変更の目的**: なぜこの変更が必要か
- **主な変更箇所**: どのファイル・コンポーネントに何をしたか
- **レビュワーが注意すべき点**: 設計判断・既知の制約・TODO など

### ステップ2: 説明を書く

以下のテンプレートを使う。セクションが不要なら省略してよい。

```markdown
## 概要

<1〜2文で変更の目的と効果を述べる>

## 変更内容

<箇条書きで主な変更を列挙。ファイル名より「何のために何をしたか」を書く>

## 注意点（任意）

<設計上の判断・既知の制約・スタブ実装・後続タスクなど、レビュワーに伝えるべきことがあれば>
```

### ステップ3: PR に反映する

**新規 PR 作成の場合:**
```bash
git push -u origin <branch>
gh pr create --title "<title>" --body "$(cat <<'EOF'
<説明>
EOF
)"
```

**既存 PR の説明を更新する場合:**
```bash
gh pr edit <number> --body "$(cat <<'EOF'
<説明>
EOF
)"
```

## 品質基準

**文字数:** 全体 800文字以内を厳守する。書き終えたら `echo -n "..." | wc -m` で確認すること。

**やること:**
- 概要は 1〜2 文に絞る
- 箇条書きは 5 項目以内を目安にする
- 「なぜ」を必ず含める（背景・目的）
- スタブ実装や TODO があれば明記する

**やらないこと:**
- diff を日本語に言い換えるだけの説明
- 表・太字の使いすぎ（読む気が失せる）
- テスト変更など自明な内容の列挙
- 700文字を超えた場合に概要・注意点セクションを削らずに箇条書きを増やす

## よくある失敗

**長すぎる説明**
- 問題: レビュワーが読まなくなる
- 対策: 概要で伝わるなら「変更内容」は省略。注意点は本当に必要な場合のみ書く

**「何を変えたか」しか書いていない**
- 問題: レビュワーが背景を理解できない
- 対策: 「なぜ変えるか」「変更後どうなるか」を先に書く
