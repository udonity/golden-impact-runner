## 1. メンタルモデル

スキルは**専門タスク向けのオンボーディングガイド**—関連する場合にClaudeが動的に読み込むモジュール式の指示パッケージである。

| 側面 | CLAUDE.md | スキル |
| ---- | --------- | ------ |
| 読み込み | 常時（起動時） | オンデマンド（トリガー時） |
| スコープ | プロジェクト全体のルール | タスク固有のワークフロー |
| コンテキストコスト | 全会話で発生 | 必要な時のみ |
| 構造 | 単一ファイル | リソース付きディレクトリ |

**CLAUDE.mdを使う場合**: 不変の規約、コーディング標準、常時有効なプロジェクトルール。
**スキルを使う場合**: 複雑なワークフロー、スクリプト、テンプレート、文脈に応じて有効化されるドメイン知識。

## 2. アーキテクチャ

### トークン読み込み階層

```
レベル1: メタデータのみ（常時読み込み）    ~100トークン
         システムプロンプト内の name + description
                    ↓
レベル2: SKILL.md本文（トリガー時）       ~1,500-5,000トークン
         スキル選択後に完全な指示を読み込み
                    ↓
レベル3: バンドルリソース（必要時）        無制限
         scripts/ references/ assets/
         Claudeが必要と判断した時のみ読み込み
```

### 選択メカニズム

**純粋なLLM推論—アルゴリズムによるマッチングなし。** Claudeは自然言語理解により全スキルの説明文を評価する。つまり:

- 説明文の品質がトリガーに**極めて重要**
- 曖昧な説明文 → スキルがトリガーされない
- 具体的なトリガーフレーズ → 確実な起動

## 3. 必須構造

```
skill-name/
├── SKILL.md                    # 必須 - 指示書 + フロントマター
├── scripts/                    # 任意 - 実行可能コード
│   └── validate.py
├── references/                 # 任意 - コンテキストに読み込まれるドキュメント
│   ├── api.md
│   └── schema.md
└── assets/                     # 任意 - 出力用ファイル（読み込まれない）
    └── template.docx
```

### フロントマター（YAML）

```yaml
---
name: processing-pdfs                    # 必須: 小文字、ハイフンのみ
description: >-                          # 必須: 何をするか + いつ使うか
  PDFファイルからテキストとテーブルを抽出し、フォームに入力し、ドキュメントを結合する。
  PDFファイルを扱う場合、またはユーザーがPDF、フォーム、ドキュメント抽出に
  言及した場合に使用。
---
```

**検証ルール:**

- `name`: 64文字以下、`[a-z0-9-]` のみ、"anthropic"/"claude" 不可
- `description`: 1024文字以下、空でないこと、XMLタグ不可

## 4. 設計原則

### 4.1 簡潔さが生存条件

コンテキストウィンドウ = 公共財。すべてのトークンが会話履歴と競合する。

**デフォルトの前提: Claudeは既に十分賢い。** Claudeが知らないことだけを追加する。

```markdown
# 悪い例（~150トークン）- 自明なことを説明
PDF（Portable Document Format）ファイルは一般的なファイル形式で...

# 良い例（~50トークン）- 能力を前提とする
## PDFテキスト抽出
pdfplumberを使用:
```python
import pdfplumber
with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
```

### 4.2 段階的開示

すべてを前面に出さない。オンデマンド読み込み用に構造化する。

```markdown
# SKILL.md内 - 概要 + ポインタ
## クイックスタート
[必須コード例]

## 機能
- **機能A**: [A.md](references/A.md) を参照
- **機能B**: [B.md](references/B.md) を参照
```

**重要ルール:**

- リファレンスはSKILL.mdから**1階層のみ**
- チェーン禁止: SKILL.md → advanced.md → details.md
- 長いファイル（100行超）: 先頭に目次を含める

### 4.3 自由度

タスクの脆弱性に応じて具体性を調整する:

| 自由度 | 適用場面 | 例 |
| ------ | -------- | -- |
| **高** | 複数の有効なアプローチがある | コードレビューガイドライン |
| **中** | 推奨パターンあり、多少のバリエーション可 | レポートテンプレート |
| **低** | 脆弱/エラーが起きやすい、一貫性が重要 | DBマイグレーションスクリプト |

## 5. 説明文の書き方

説明文は**唯一の**トリガー機構である。

### ルール

1. **常に三人称** — "Excelファイルを処理する" であって "私が手伝います" ではない
2. **具体的 + トリガーフレーズ** — 何をするか AND いつ起動するかを含む
3. **発見性のためのキーワード** — ユーザーが使いそうな類義語を含む

### 例

```yaml
# 良い例 - 具体的、トリガーを含む
description: >-
  Excelスプレッドシートの分析、ピボットテーブルの作成、チャートの生成を行う。
  Excelファイル、スプレッドシート、表形式データ、.xlsxファイルの分析時に使用。

# 良い例 - アクション + コンテキスト
description: >-
  gitの差分を分析して説明的なコミットメッセージを生成する。
  ユーザーがコミットメッセージの作成やステージされた変更のレビューを依頼した時に使用。

# 悪い例 - 曖昧
description: ドキュメントを支援する
description: データを処理する
```

**動名詞形（動詞 + -ing）を推奨**:

```
✓ processing-pdfs
✓ analyzing-spreadsheets
✓ testing-code

✗ helper, utils, tools（曖昧）
✗ documents, data, files（一般的）
✗ anthropic-helper, claude-tools（予約済み）
```

## 7. バンドルリソース

### scripts/ — 実行可能コード

**使用場面:** 同じコードを繰り返し書き直す場合、決定論的な信頼性が必要な場合。

**利点:**

- トークン効率が良い（読み込まずに実行）
- 決定論的（生成のバラつきなし）
- 使用間で一貫性がある

**SKILL.md内での記述:**
```markdown
# 実行（最も一般的）
`python scripts/validate.py input.pdf` を実行

# リファレンスとして読む（稀）
検証アルゴリズムは `scripts/validate.py` を参照
```

### references/ — コンテキストに読み込まれるドキュメント

**使用場面:** Claudeが作業中に参照すべきドキュメント。

```
references/
├── schema.md       # データベーススキーマ
├── api.md          # API仕様
├── policies.md     # 社内ルール
```

**大きなファイル（1万語超）:** SKILL.md内にgrepパターンを含めて、対象を絞ったアクセスを可能にする。

### assets/ — 出力ファイル（読み込まれない）

**使用場面:** 出力に使用するファイル、指示コンテキストではないもの。

Claudeはパスで参照し、コピー/修正する—コンテキストには読み込まない。

## 8. ワークフローパターン

### チェックリストパターン

```markdown
## フォーム入力ワークフロー

コピーして進捗を管理:
- [ ] ステップ1: フォームを分析
- [ ] ステップ2: フィールドマッピングを作成
- [ ] ステップ3: マッピングを検証
- [ ] ステップ4: フォームに入力
```

### フィードバックループパターン

```markdown
## 検証ループ

1. 編集を行う
2. **即座に検証**: `python scripts/validate.py`
3. 検証失敗の場合: 修正して再実行
4. **検証に合格してから次に進む**
```

### 条件分岐ワークフローパターン

```markdown
## ドキュメント修正

1. 種類を判定:
   - **新規作成？** → 「作成ワークフロー」に従う
   - **既存を編集？** → 「編集ワークフロー」に従う
```

### テンプレートパターン

```markdown
## レポート構造

必ずこのテンプレートを使用する:

```markdown
# [タイトル]

## エグゼクティブサマリー
[1段落の概要]

## 主要な発見
- 発見1
- 発見2
```
```

## 9. アンチパターン

### 含めてはいけないもの
- README.md、CHANGELOG.md、INSTALLATION_GUIDE.md
- ユーザー向けドキュメント
- セットアップ/テスト手順

スキルは**AIエージェント向け**であり、人間向けではない。

### やってはいけないこと

| アンチパターン | 問題点 | 修正方法 |
| -------------- | ------ | -------- |
| Windowsパス | Unixで動作しない | フォワードスラッシュを使用 |
| ネストされたリファレンス | 部分的な読み込み | 1階層のみ |
| 時間依存の情報 | 古くなる | 「レガシー」セクションを使用 |
| 選択肢過多 | 混乱する | デフォルトを提供 |
| 曖昧な説明文 | トリガーされない | 具体的 + トリガー |
| 用語の不統一 | Claudeが混乱する | 1つの用語に統一 |
| マジックナンバー | 検証不能 | 理由を文書化 |

### 悪い例: デフォルトなしの複数選択肢

```markdown
# 悪い例
"pypdf、pdfplumber、PyMuPDFが使えます..."

# 良い例
"テキスト抽出にはpdfplumberを使用:
[コード]
スキャンPDFの場合は、代わりにpdf2imageとpytesseractを使用。"
```

## 10. 高度なパターン

### 「THE EXACT PROMPT」パターン

再現可能なプロンプトをエンコードする:

```markdown
## THE EXACT PROMPT — プランレビュー

```
このプラン全体を慎重にレビューしてください...
```
```

### 「なぜこれが存在するか」セクション

動機を前面に出す:

```markdown
## なぜこれが存在するか

複数のAIエージェントの管理は大変:
- **ウィンドウの混乱**: 各エージェントに専用ターミナルが必要
- **コンテキストスイッチ**: フローが途切れる
```

### リスク階層テーブル

安全性/セキュリティスキル向け:

```markdown
| 階層 | 承認 | 自動承認 | 例 |
| ---- | ---- | -------- | -- |
| **重大** | 2人以上 | 不可 | `rm -rf /` |
| **危険** | 1人 | 不可 | `git reset --hard` |
| **注意** | 0人 | 30秒後 | `rm file.txt` |
```

### 終了コード標準化

```markdown
## 終了コード

| コード | 意味 |
| ------ | ---- |
| `0` | 成功 |
| `1` | エラー |
| `2` | 無効な引数 |
```
