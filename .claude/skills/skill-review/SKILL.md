# スキルレビュー

## 概要

エージェントスキルをAgent Skills標準およびベストプラクティスに基づいて検証する。構造、フロントマター、説明文の品質、段階的開示、一般的なアンチパターンをレビューする。

## 使用タイミング

- ユーザーがスキルのレビューまたは検証を依頼した場合
- ユーザーが新しいスキルを作成中でフィードバックを求めている場合
- ユーザーが「このスキルはよく書けている？」と質問した場合
- ユーザーがスキルの品質、ベストプラクティス、改善について言及した場合

## レビュープロセス

### フェーズ1: リファレンスの読み込み

レビュー前に以下を読み込む:

- `references/best-practices.md` — 包括的なガイドライン
- `references/checklist.md` — 簡易検証チェックリスト

### フェーズ2: 対象の特定

レビュー対象を決定する:

- **単一スキル**: `skills/<名前>/SKILL.md` とその構造をレビュー
- **全スキル**: `skills/` ディレクトリ全体を監査
- **新規スキル草案**: 作成前に提供された内容をレビュー

### フェーズ3: 構造監査

スキルディレクトリ構造をチェックする:

```
skill-name/
├── SKILL.md              # 必須
├── references/           # 任意 - 読み込まれるドキュメント
├── scripts/              # 任意 - 実行可能コード
└── assets/               # 任意 - 出力ファイル（読み込まれない）
```

**確認項目:**

- [ ] SKILL.md が存在する
- [ ] ディレクトリ名がフロントマターの `name` と一致する
- [ ] リファレンスは1階層のみ（ネストチェーンなし）
- [ ] スクリプトはフォワードスラッシュを使用（Windowsパスなし）
- [ ] 不要なファイルがない（README.md、CHANGELOG.md など）
- [ ] SKILL.md本文中のスクリプトパス（`scripts/foo.py`）がディレクトリに存在する
- [ ] スクリプトが外部バイナリを使用する場合、依存関係が文書化されている

### フェーズ4: フロントマター検証

YAMLフロントマターをチェックする:

```yaml
---
name: skill-name # 必須: 小文字、ハイフン、64文字以下
description: >- # 必須: 1024文字以下、三人称
  何をするか。いつ使うか。
---
```

**検証項目:**

- [ ] `name`: 小文字とハイフンのみ（`[a-z0-9-]`）
- [ ] `name`: 64文字以下
- [ ] `name`: "anthropic" や "claude" を含まない
- [ ] `description`: 空でない、1024文字以下
- [ ] `description`: 三人称（"I can" や "You can" ではない）
- [ ] `description`: 何をするか AND いつトリガーするかを含む
- [ ] `description`: 具体的なトリガーフレーズを含む

### フェーズ5: 説明文の品質

説明文は**唯一の**トリガー機構である。以下を評価する:

**良い説明文の特徴:**

- 具体的なアクション: "PDFファイルからテキストとテーブルを抽出する"
- トリガーフレーズ: "Excelファイル、スプレッドシート、.xlsxの分析時に使用"
- ユーザーが使いそうな類義語: "表形式データ、CSV、ワークブック"

**悪い説明文:**

- 曖昧: "ドキュメントを支援する"
- 一般的: "データを処理する"
- トリガーなし: "スプレッドシートを分析する"（「いつ使うか」がない）

### フェーズ6: 本文分析

SKILL.md の本文内容をレビューする:

**行数:**

- [ ] 500行未満（`wc -l` で確認）
- [ ] 超過する場合はリファレンスファイルに分割する

**段階的開示:**

- [ ] クイックスタートまたは概要が上部にある
- [ ] 詳細は references/ に移動されている
- [ ] 長いリファレンスファイル（100行超）には目次がある
- [ ] リファレンスポインタが条件付きである（「〜の場合 → reference.md」形式）
- [ ] 無条件ポインタ（必須セクション内や手順フロー内）が references/ を指していない

**トークン効率:**

- [ ] 自明な説明がない（Claudeは既に知っている）
- [ ] 冗長な文章より例示を優先
- [ ] 各行がトークンコストに見合っている
- [ ] references/ の総行数が SKILL.md 本文の3倍以内（超過する場合はコード例の骨格化を検討）

**自由度:**

- [ ] コンテキスト依存タスクには高い自由度
- [ ] 脆弱/エラーが起きやすいタスクには低い自由度
- [ ] 複数の選択肢がある場合はデフォルトを提供

### フェーズ7: アンチパターンチェック

一般的な問題をスキャンする:

| アンチパターン | 確認ポイント |
| --- | --- |
| Windowsパス | `scripts\file.py` → `scripts/file.py` にすべき |
| ネストされたリファレンス | A.md → B.md → C.md のチェーン |
| 時間依存の情報 | "2025年8月以前なら..." |
| マジックナンバー | 説明のない値 |
| 選択肢過多 | "X、Y、Zが使えます..." でデフォルトなし |
| 用語の不統一 | "endpoint"/"URL"/"route" の混在 |
| ユーザー向けドキュメント | README、CHANGELOG、インストールガイド |
| 一人称/二人称の説明文 | "I can help" や "You can use" |
| 無条件リファレンスポインタ | 「必須要素（詳細は ref.md 参照）」→ 条件付き読み込み指示にすべき |
| リファレンス肥大化 | references/ 総量が SKILL.md の3倍超 → コード例の骨格化を検討 |

### フェーズ8: 結果報告

以下の形式で結果を報告する:

````markdown
## スキルレビュー: [skill-name]

### サマリー
[1-2文の総合評価]

### 構造
[✓/✗] ディレクトリ構成
[✓/✗] ファイルの存在
[✓/✗] リファレンスの深さ

### フロントマター
[✓/✗] name の検証
[✓/✗] description の検証

### 説明文の品質
**スコア**: [良好 / 許容範囲 / 要改善]
**問題点**: [具体的な問題のリスト]
**修正案**（必要な場合）:
```yaml
description: >-
  [改善された説明文]
```

### 本文分析

**行数**: [X] 行
**トークン効率**: [良好 / 削減可能]
**段階的開示**: [✓/✗]

### 検出されたアンチパターン

- [問題1] — 場所: `file:line`
- [問題2] — 場所: `file:line`

### 推奨事項

1. [実行可能な修正]
2. [実行可能な修正]
````
