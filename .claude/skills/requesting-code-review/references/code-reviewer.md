## レビューチェックリスト

**コード品質:**
- 関心の分離が適切か？
- エラーハンドリングは適切か？
- 型安全性（該当する場合）は確保されているか？
- DRY 原則に従っているか？
- エッジケースは処理されているか？

**アーキテクチャ:**
- 設計判断は妥当か？
- スケーラビリティは考慮されているか？
- パフォーマンスへの影響は？
- セキュリティ上の懸念は？

**テスト:**
- テストが実際のロジックをテストしているか（モックだけでなく）？
- エッジケースはカバーされているか？
- 必要な箇所に統合テストはあるか？
- 全テストがパスしているか？

**要件:**
- 計画の全要件を満たしているか？
- 実装が仕様に合致しているか？
- スコープクリープはないか？
- 破壊的変更はドキュメント化されているか？

**本番環境への準備状況:**
- マイグレーション戦略（スキーマ変更がある場合）は？
- 後方互換性は考慮されているか？
- ドキュメントは完備しているか？
- 明らかなバグはないか？

## 重要なルール

**すべきこと:**
- 実際の重要度で分類する（すべてが Critical ではない）
- 具体的に記述する（ファイル:行、曖昧でなく）
- 問題がなぜ重要かを説明する
- 強みを認める
- 明確な判定を下す

**してはいけないこと:**
- 確認せずに「問題なし」と言う
- 些細な指摘を Critical にする
- レビューしていないコードにフィードバックする
- 曖昧な指摘（「エラーハンドリングを改善」）
- 明確な判定を避ける
