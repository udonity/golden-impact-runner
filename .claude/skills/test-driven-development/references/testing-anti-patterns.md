# テストのアンチパターン

**このリファレンスを読むタイミング:** テストの作成・変更時、モックの追加時、またはプロダクションコードにテスト専用メソッドを追加したくなったとき。

## 概要

テストはモックの振る舞いではなく、実際の振る舞いを検証しなければならない。モックは分離のための手段であり、テスト対象ではない。

**基本原則:** モックが何をするかではなく、コードが何をするかをテストせよ。

**厳格なTDDに従えば、これらのアンチパターンは防げる。**

## 鉄の掟

```
1. モックの振る舞いをテストしてはならない
2. プロダクションクラスにテスト専用メソッドを追加してはならない
3. 依存関係を理解せずにモックしてはならない
```

## アンチパターン1: モックの振る舞いをテストする

**違反例:**
```typescript
// BAD: モックの存在をテストしている
test('サイドバーを表示する', () => {
  render(<Page />);
  expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
});
```

**なぜこれが間違いか:**
- モックが動くことを検証しており、コンポーネントが動くことを検証していない
- モックが存在すればテストが通り、なければ失敗する
- 実際の振る舞いについて何もわからない

**あなたの人間パートナーの指摘:** 「モックの振る舞いをテストしていないか？」

**修正方法:**
```typescript
// GOOD: 実際のコンポーネントをテストするか、モックしない
test('サイドバーを表示する', () => {
  render(<Page />);  // サイドバーをモックしない
  expect(screen.getByRole('navigation')).toBeInTheDocument();
});

// または分離のためにサイドバーをモックする必要がある場合:
// モックに対してアサートしない - サイドバーが存在する状態でのPageの振る舞いをテストする
```

### ゲート関数

```
モック要素に対してアサートする前に:
  問う: 「実際のコンポーネントの振る舞いをテストしているか、単にモックの存在を確認しているだけか？」

  モックの存在をテストしている場合:
    やめよ - アサーションを削除するか、コンポーネントのモックを解除する

  代わりに実際の振る舞いをテストせよ
```

## アンチパターン2: プロダクションにテスト専用メソッド

**違反例:**
```typescript
// BAD: destroy()はテストでのみ使用される
class Session {
  async destroy() {  // プロダクションAPIに見える！
    await this._workspaceManager?.destroyWorkspace(this.id);
    // ... クリーンアップ
  }
}

// テスト内で
afterEach(() => session.destroy());
```

**なぜこれが間違いか:**
- プロダクションクラスがテスト専用コードで汚染される
- プロダクションで誤って呼び出されると危険
- YAGNIと関心の分離に違反する
- オブジェクトのライフサイクルとエンティティのライフサイクルを混同する

**修正方法:**
```typescript
// GOOD: テストユーティリティがテストのクリーンアップを処理する
// Sessionにdestroy()はない - プロダクションではステートレス

// test-utils/ 内
export async function cleanupSession(session: Session) {
  const workspace = session.getWorkspaceInfo();
  if (workspace) {
    await workspaceManager.destroyWorkspace(workspace.id);
  }
}

// テスト内で
afterEach(() => cleanupSession(session));
```

### ゲート関数

```
プロダクションクラスにメソッドを追加する前に:
  問う: 「これはテストでのみ使われるか？」

  はいの場合:
    やめよ - 追加するな
    代わりにテストユーティリティに配置する

  問う: 「このクラスはこのリソースのライフサイクルを所有しているか？」

  いいえの場合:
    やめよ - このメソッドを置くべきクラスが違う
```

## アンチパターン3: 理解せずにモックする

**違反例:**
```typescript
// BAD: モックがテストのロジックを壊している
test('重複サーバーを検出する', () => {
  // モックがテストに必要な設定の書き込みを妨げている！
  vi.mock('ToolCatalog', () => ({
    discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
  }));

  await addServer(config);
  await addServer(config);  // スローすべきだが - しない！
});
```

**なぜこれが間違いか:**
- モックされたメソッドにテストが依存する副作用があった（設定の書き込み）
- 「安全のために」過剰にモックすると実際の振る舞いが壊れる
- テストが間違った理由で通るか、不可解に失敗する

**修正方法:**
```typescript
// GOOD: 正しいレベルでモックする
test('重複サーバーを検出する', () => {
  // 遅い部分をモックし、テストに必要な振る舞いは保持する
  vi.mock('MCPServerManager'); // 遅いサーバー起動だけモックする

  await addServer(config);  // 設定が書き込まれる
  await addServer(config);  // 重複が検出される
});
```

### ゲート関数

```
メソッドをモックする前に:
  やめよ - まだモックするな

  1. 問う: 「実際のメソッドにはどんな副作用があるか？」
  2. 問う: 「このテストはその副作用に依存しているか？」
  3. 問う: 「このテストに何が必要か完全に理解しているか？」

  副作用に依存している場合:
    より低いレベルでモックする（実際の遅い/外部操作）
    または必要な振る舞いを保持するテストダブルを使う
    テストが依存する高レベルメソッドをモックしない

  テストに何が必要かわからない場合:
    まず実際の実装でテストを実行する
    実際に何が起こる必要があるか観察する
    それから正しいレベルで最小限のモックを追加する

  レッドフラグ:
    - 「安全のためにモックしよう」
    - 「遅いかもしれないからモックしよう」
    - 依存チェーンを理解せずにモックする
```

## アンチパターン4: 不完全なモック

**違反例:**
```typescript
// BAD: 部分的なモック - 必要だと思うフィールドだけ
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' }
  // 不足: 下流のコードが使うmetadata
};

// 後で: コードがresponse.metadata.requestIdにアクセスして壊れる
```

**なぜこれが間違いか:**
- **部分的なモックは構造の仮定を隠す** - 知っているフィールドだけモックした
- **下流のコードが含めなかったフィールドに依存するかもしれない** - サイレントな失敗
- **テストは通るが結合テストで失敗する** - モックは不完全、実際のAPIは完全
- **偽の信頼** - テストは実際の振る舞いについて何も証明しない

**鉄の掟:** テストが直接使うフィールドだけでなく、現実に存在する完全なデータ構造をモックせよ。

**修正方法:**
```typescript
// GOOD: 実際のAPIの完全性を反映する
const mockResponse = {
  status: 'success',
  data: { userId: '123', name: 'Alice' },
  metadata: { requestId: 'req-789', timestamp: 1234567890 }
  // 実際のAPIが返すすべてのフィールド
};
```

### ゲート関数

```
モックレスポンスを作成する前に:
  確認: 「実際のAPIレスポンスにはどんなフィールドが含まれるか？」

  アクション:
    1. ドキュメント/例から実際のAPIレスポンスを調べる
    2. システムが下流で消費する可能性のあるすべてのフィールドを含める
    3. モックが実際のレスポンススキーマと完全に一致することを確認する

  重要:
    モックを作成するなら、構造全体を理解しなければならない
    部分的なモックは、省略されたフィールドにコードが依存するとサイレントに失敗する

  不確かな場合: 文書化されたすべてのフィールドを含める
```

## アンチパターン5: 後付けの結合テスト

**違反例:**
```
実装完了
テスト未作成
「テストの準備ができました」
```

**なぜこれが間違いか:**
- テストは実装の一部であり、オプションのフォローアップではない
- TDDならこれを防げた
- テストなしに完了とは言えない

**修正方法:**
```
TDDサイクル:
1. 失敗するテストを書く
2. 通るように実装する
3. リファクタリングする
4. それから完了と言う
```

## モックが複雑になりすぎたとき

**警告サイン:**
- モックのセットアップがテストロジックより長い
- テストを通すためにすべてをモックしている
- モックに実際のコンポーネントが持つメソッドが欠けている
- モックが変わるとテストが壊れる

**あなたの人間パートナーの質問:** 「ここでモックを使う必要があるか？」

**検討:** 実際のコンポーネントを使った結合テストは、複雑なモックより簡単なことが多い

## TDDがこれらのアンチパターンを防ぐ理由

**TDDが役立つ理由:**
1. **テストを先に書く** → 実際に何をテストしているか考えることを強制する
2. **失敗を確認する** → テストがモックではなく実際の振る舞いをテストしていることを確認する
3. **最小限の実装** → テスト専用メソッドが忍び込まない
4. **実際の依存関係** → モックする前にテストが実際に何を必要としているか見える

**モックの振る舞いをテストしているなら、TDDに違反している** - 実際のコードに対するテストの失敗を確認する前にモックを追加した。

## クイックリファレンス

| アンチパターン | 修正方法 |
|--------------|-----|
| モック要素に対するアサート | 実際のコンポーネントをテストするかモックを解除する |
| プロダクションのテスト専用メソッド | テストユーティリティに移動する |
| 理解せずにモック | まず依存関係を理解し、最小限にモックする |
| 不完全なモック | 実際のAPIを完全に反映する |
| 後付けのテスト | TDD - テストファースト |
| 過剰に複雑なモック | 結合テストを検討する |

## レッドフラグ

- `*-mock` テストIDに対するアサーション
- テストファイルからのみ呼ばれるメソッド
- モックのセットアップがテストの50%以上
- モックを除去するとテストが失敗する
- モックが必要な理由を説明できない
- 「安全のために」モックする

## 結論

**モックは分離のためのツールであり、テスト対象ではない。**

TDDでモックの振る舞いをテストしていることが判明したら、間違った方向に進んでいる。

修正方法: 実際の振る舞いをテストするか、そもそもなぜモックしているのか問い直せ。
