# Serena プロジェクトメモリの更新

## 概要

プロジェクトメモリは将来のエージェントセッションに引き継がれる**唯一の長期記憶**である。  
メモリは**AIエージェント向けの操作知識**であり、人間向けドキュメントではない。

**基本原則:** タスク中に新しいプロジェクト固有の知識を得たら、必ずメモリを更新せよ。

## セッション開始時の必須ワークフロー

```
[MANDATORY - 省略不可]
1. mcp_serena_list_memories   → 既存メモリ一覧を確認
2. mcp_serena_read_memory     → 関連するメモリを読む
→ 30秒の投資が、間違った実装の数時間を防ぐ
```

**緊急時でも省略禁止。** 「単純な機能だから不要」「緊急だから後で」は常に誤った合理化。

## いつ使うか

| トリガー | 例 |
|---|---|
| 新しいアーキテクチャパターン・規約を発見した | `03_domain` に AWS SDK import 禁止を確認 |
| 新しいコマンド・スクリプトを使った | 新しい `pnpm run` スクリプトを実行 |
| 既存メモリの情報が古い・不正確と気づいた | パッケージ追加でスタック情報が変わった |
| 新しいパッケージ・モジュールが追加された | 新しいバッチが workspace に追加 |
| 重要な設計判断・禁止事項を確認した | 「DynamoDB `scan` 禁止」を実地で確認 |

**使わない場合:** 正常なタスク遂行のみ（新知識なし）/ 一時的・タスク固有の情報 / 既記録済みの情報

## メモリツール一覧

メモリツールが利用不可な場合は、先に `mcp_serena_activate_memory_management_tools` を実行してツールを有効化する。

| ツール | 用途 |
|---|---|
| `mcp_serena_list_memories` | 既存メモリ一覧確認（最初に必ず実行） |
| `mcp_serena_read_memory` | メモリ内容確認 |
| `mcp_serena_write_memory` | **新規**メモリ作成 |
| `mcp_serena_edit_memory` | 既存メモリの**部分更新**（上書き事故防止のため優先） |
| `mcp_serena_delete_memory` | 削除（必ずユーザー許可を取ること） |
| `mcp_serena_rename_memory` | メモリ名変更・階層整理 |

## 標準メモリカテゴリ

| メモリ名 | 記録すべき内容 |
|---|---|
| `conventions` | TypeScript ルール・命名規則・禁止事項・完了チェックリスト |
| `project_overview` | Tech stack・アーキテクチャ・パッケージ一覧 |
| `suggested_commands` | ビルド・テスト・デプロイ・ユーティリティコマンド |

サブトピック: `architecture/domain-rules`、`packages/api` など `/` で階層化。

## 手順

**Step 1:** `mcp_serena_list_memories` → 既存メモリ確認  
**Step 2:** 対象があれば `mcp_serena_read_memory` で現内容を確認（重複・矛盾を防ぐ）  
**Step 3:** 新カテゴリなら `write_memory`、既存への追記なら `edit_memory`

## 良いメモリの書き方

**必須要素:**

- 具体的なファイルパス（`src/middleware/errorHandler.ts`）
- コードスニペット（rationale 付き）
- 関連メモリへのクロスリファレンス
- なぜそのパターンが存在するかの理由

| 良い例 | 悪い例 |
|---|---|
| 「`04_infrastructure/` にリポジトリ実装。DI は `config/di/` に集約」 | 「インフラ層がある。ファイルが整理されている」 |
| 「`scan` 禁止 → コスト爆発防止。`query`/`getItem` を使う」 | 「DynamoDB のベストプラクティスに従う」 |

## リファレンスの使い分け

以下の条件に該当する場合のみ、対応するリファレンスを読み込む:

- **初めてメモリを作成する場合** → [good-memory-example.md](references/good-memory-example.md) で構造を確認
- **メモリの品質に自信がない場合** → [bad-memory-example.md](references/bad-memory-example.md) でアンチパターンを確認
- **プロジェクト初期オンボーディング時** → [onboarding-memory-set-example.md](references/onboarding-memory-set-example.md) で初期セット構成を確認

## アンチパターン（TDDテストで発見・実証済み）

### Anti-Pattern 1: メモリの代わりにドキュメントファイルを作成する

「DEVELOPMENT-GUIDE.md を作ればチームと共有できる」という誘惑に負けること。
→ **メモリの対象読者はAIエージェント**。人間向けドキュメントが必要なら別途・明示的に作る。
→ 「両方作れば安心」も誤り。冗長性がプロジェクトを汚染する。

### Anti-Pattern 2: 緊急時にメモリ読み込みをスキップする

「本番バグで10分しかない、メモリを読む時間はない」という合理化。
→ **30秒の投資は常に見合う**。コンテキストなしの修正は誤実装のリスクが高い。

### Anti-Pattern 3: ヘッジング（決断の先送り）

「ドキュメントにしますか？メモリにしますか？」とユーザーに選択を委ねること。  
→ **自分で判断して実行し、理由を説明せよ。許可を求めるな。**

```
[BAD]  「メモリを作りましょうか、それともドキュメントにしますか？」
[GOOD] 「デプロイパターンのメモリを作成しました。AIエージェントが次のセッションで参照します。
        チーム向け手順書が別途必要な場合は、対象読者と用途を教えてください。」
```

## よくある間違い

| 間違い | 正しい行動 |
|---|---|
| 確認せず `write_memory` で上書き | 先に `list_memories` → `read_memory` で確認 |
| メモリ名に日本語・スペースを使う | 英語・ハイフン・スラッシュのみ（`architecture/domain-rules`） |
| タスク固有の一時情報を記録する | 複数セッションで再利用できる知識のみ記録 |
| セッション終了時にメモリ更新を忘れる | タスク完了前に必ずメモリ更新を確認 |
| ユーザーの許可なく `delete_memory` を実行する | `edit_memory` で修正するか、明示的な許可を取る |
