# 体系的デバッグ

## 概要

場当たり的な修正は時間を浪費し、新たなバグを生む。安易なパッチは根本的な問題を隠してしまう。

**基本原則:** 修正を試みる前に、必ず根本原因を特定すること。症状への修正は失敗である。

**このプロセスの文言に違反することは、デバッグの精神に違反することである。**

## 鉄の掟

```
根本原因の調査なしに修正を行ってはならない
```

フェーズ1を完了していなければ、修正を提案することはできない。

## いつ使うか

あらゆる技術的問題に使用する:
- テスト失敗
- 本番環境のバグ
- 予期しない動作
- パフォーマンス問題
- ビルド失敗
- インテグレーションの問題

**特に以下の場合に使用すること:**
- 時間的プレッシャーがある時（緊急事態は当て推量を誘発する）
- 「ちょっとした修正ですぐ直る」と思える時
- すでに複数の修正を試した後
- 前回の修正がうまくいかなかった時
- 問題を完全に理解できていない時

**以下の場合もスキップしないこと:**
- 問題が単純に見える時（単純なバグにも根本原因はある）
- 急いでいる時（急ぐことは手戻りを保証する）
- マネージャーが「今すぐ直せ」と言っている時（体系的なアプローチは無秩序な試行より速い）

## 4つのフェーズ

各フェーズを完了してから次に進まなければならない。

### フェーズ1: 根本原因の調査

**修正を試みる前に:**

1. **エラーメッセージを注意深く読む**
   - エラーや警告を読み飛ばさない
   - 多くの場合、正確な解決策が含まれている
   - スタックトレースを最後まで読む
   - 行番号、ファイルパス、エラーコードをメモする

2. **一貫して再現する**
   - 確実にトリガーできるか？
   - 正確な手順は？
   - 毎回発生するか？
   - 再現できない場合 → データを集める、推測しない

3. **最近の変更を確認する**
   - この問題を引き起こし得る変更は何か？
   - Git diff、最近のコミット
   - 新しい依存関係、設定変更
   - 環境の違い

4. **マルチコンポーネントシステムでエビデンスを収集する**

   **システムが複数のコンポーネントを持つ場合（CI → ビルド → 署名、API → サービス → データベース）:**

   **修正を提案する前に、診断用の計装を追加する:**
   ```
   各コンポーネント境界に対して:
     - コンポーネントに入るデータをログに記録
     - コンポーネントから出るデータをログに記録
     - 環境/設定の伝播を検証
     - 各レイヤーの状態を確認

   一度実行してどこで壊れているかを示すエビデンスを収集
   エビデンスを分析して障害コンポーネントを特定
   その特定のコンポーネントを調査
   ```

   **例（マルチレイヤーシステム）:**
   ```bash
   # レイヤー1: ワークフロー
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # レイヤー2: ビルドスクリプト
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # レイヤー3: 署名スクリプト
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # レイヤー4: 実際の署名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **これにより判明すること:** どのレイヤーが失敗しているか（secrets → workflow OK、workflow → build NG）

5. **データフローをトレースする**

   **エラーがコールスタックの深い位置にある場合:**

   完全な逆方向トレーシング技法については、このディレクトリの `references/root-cause-tracing.md` を参照。

   **簡易版:**
   - 不正な値はどこで発生したか？
   - 誰がこの不正な値でこれを呼び出したか？
   - ソースが見つかるまでトレースを続ける
   - 症状ではなくソースで修正する

### フェーズ2: パターン分析

**修正する前にパターンを見つける:**

1. **動作する例を見つける**
   - 同じコードベースにある類似の動作するコードを探す
   - 壊れているものと類似して動作しているものは何か？

2. **リファレンスと比較する**
   - パターンを実装する場合、リファレンス実装を完全に読む
   - 流し読みしない - すべての行を読む
   - 適用する前にパターンを完全に理解する

3. **差異を特定する**
   - 動作するものと壊れているものの違いは何か？
   - どんなに小さくても、すべての違いをリストアップする
   - 「それは関係ない」と決めつけない

4. **依存関係を理解する**
   - これは他にどんなコンポーネントが必要か？
   - どんな設定、構成、環境が必要か？
   - どんな前提を置いているか？

### フェーズ3: 仮説と検証

**科学的手法:**

1. **単一の仮説を立てる**
   - 明確に述べる: 「Yという理由で、Xが根本原因だと考える」
   - 書き留める
   - 曖昧ではなく具体的にする

2. **最小限のテストを行う**
   - 仮説を検証するための最小の変更を行う
   - 一度に一つの変数だけ
   - 複数のものを同時に修正しない

3. **続ける前に検証する**
   - うまくいったか？ はい → フェーズ4
   - うまくいかなかった？ 新しい仮説を立てる
   - さらに修正を追加しない

4. **わからない場合**
   - 「Xがわからない」と言う
   - わかったふりをしない
   - 助けを求める
   - さらに調査する

### フェーズ4: 実装

**症状ではなく根本原因を修正する:**

1. **失敗するテストケースを作成する**
   - 可能な限り単純な再現
   - 可能なら自動テスト
   - フレームワークがなければ使い捨てスクリプト
   - 修正前に必ず用意する
   - 適切な失敗テストの作成には `superpowers:test-driven-development` スキルを使用する

2. **単一の修正を実装する**
   - 特定した根本原因に対処する
   - 一度に一つの変更
   - 「ついでに」の改善はしない
   - リファクタリングをバンドルしない

3. **修正を検証する**
   - テストが通るようになったか？
   - 他のテストが壊れていないか？
   - 問題は本当に解決したか？

4. **修正がうまくいかない場合**
   - 停止する
   - 数える: これまでいくつの修正を試したか？
   - 3回未満: フェーズ1に戻り、新しい情報で再分析
   - **3回以上: 停止してアーキテクチャを疑う（下記ステップ5）**
   - アーキテクチャの議論なしに4回目の修正を試みない

5. **3回以上の修正が失敗した場合: アーキテクチャを疑う**

   **アーキテクチャ上の問題を示すパターン:**
   - 各修正が新たな共有状態/結合/別の場所の問題を露呈する
   - 修正の実装に「大規模なリファクタリング」が必要
   - 各修正が別の場所で新たな症状を生む

   **停止して根本を疑う:**
   - このパターンは根本的に健全か？
   - 「惰性で続けているだけ」ではないか？
   - 症状の修正を続けるよりアーキテクチャをリファクタリングすべきか？

   **さらなる修正を試みる前に、あなたの人間パートナーと議論する**

   これは仮説の失敗ではない - これはアーキテクチャの間違いである。

## 危険信号 - 停止してプロセスに従うこと

以下のように考えている自分に気づいたら:
- 「今はとりあえずの修正で、調査は後で」
- 「とりあえずXを変えてみて、うまくいくか見てみよう」
- 「複数の変更を追加して、テストを実行」
- 「テストを飛ばして、手動で確認しよう」
- 「たぶんXだろう、それを直そう」
- 「完全には理解していないが、これでうまくいくかもしれない」
- 「パターンではXと言っているが、別のやり方で適用しよう」
- 「主な問題はこれだ: [調査なしに修正をリストアップ]」
- データフローのトレース前に解決策を提案する
- **「もう一回だけ修正を試みる」（すでに2回以上試した後）**
- **各修正が別の場所で新たな問題を露呈する**

**これらすべてが意味すること: 停止。フェーズ1に戻る。**

**3回以上の修正が失敗した場合:** アーキテクチャを疑う（フェーズ4.5参照）

## あなたの人間パートナーからの「間違ったやり方をしている」サイン

**以下のリダイレクトに注意:**
- 「それは起きていないのでは？」 - 検証せずに仮定した
- 「それで分かるのか...？」 - エビデンス収集を追加すべきだった
- 「推測をやめろ」 - 理解せずに修正を提案している
- 「じっくり考えろ」 - 症状だけでなく根本を疑え
- 「詰まったのか？」（苛立ち） - あなたのアプローチがうまくいっていない

**これらを見たら:** 停止。フェーズ1に戻る。

## よくある合理化

| 言い訳 | 現実 |
|--------|---------|
| 「問題は単純だ、プロセスは不要」 | 単純な問題にも根本原因はある。単純なバグにはプロセスも速い。 |
| 「緊急事態だ、プロセスの時間がない」 | 体系的デバッグは当て推量の繰り返しより速い。 |
| 「まずこれを試してから調査しよう」 | 最初の修正がパターンを決める。最初から正しくやれ。 |
| 「修正がうまくいくのを確認してからテストを書く」 | テストされていない修正は定着しない。テストを先に書けば証明できる。 |
| 「複数の修正を同時にやれば時間の節約になる」 | 何がうまくいったか切り分けできない。新しいバグの原因になる。 |
| 「リファレンスが長すぎるので、パターンを適応する」 | 部分的な理解はバグを保証する。最後まで読め。 |
| 「問題が見えた、直そう」 | 症状が見えること ≠ 根本原因の理解。 |
| 「もう一回だけ修正を試みる」（2回以上失敗後） | 3回以上の失敗 = アーキテクチャの問題。パターンを疑え、再度修正するな。 |

## クイックリファレンス

| フェーズ | 主な活動 | 成功基準 |
|-------|---------------|------------------|
| **1. 根本原因** | エラーを読む、再現する、変更を確認、エビデンス収集 | 何がどうしてを理解する |
| **2. パターン** | 動作する例を見つける、比較する | 差異を特定する |
| **3. 仮説** | 理論を立てる、最小限のテスト | 確認または新しい仮説 |
| **4. 実装** | テスト作成、修正、検証 | バグ解決、テスト合格 |

## プロセスで「根本原因なし」と判明した場合

体系的な調査により、問題が本当に環境依存、タイミング依存、または外部要因であることが判明した場合:

1. プロセスは完了している
2. 調査した内容を文書化する
3. 適切な対処を実装する（リトライ、タイムアウト、エラーメッセージ）
4. 将来の調査のためにモニタリング/ログを追加する

**ただし:** 「根本原因なし」の95%のケースは、不完全な調査である。

## 実際の影響

デバッグセッションからの実績:
- 体系的アプローチ: 修正まで15-30分
- 場当たり的な修正アプローチ: 2-3時間の試行錯誤
- 初回修正成功率: 95% vs 40%
- 導入される新しいバグ: ほぼゼロ vs 頻発
