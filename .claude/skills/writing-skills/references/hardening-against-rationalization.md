# 合理化に対するスキルの防弾化

規律を強制するスキル（TDDなど）は合理化に耐える必要がある。エージェントは賢く、プレッシャー下では抜け穴を見つける。

**心理学ノート:** 説得テクニックがなぜ機能するかを理解すれば、体系的に適用できる。権威、コミットメント、希少性、社会的証明、一体感の原則の研究基盤については、persuasion-principles.md（Cialdini, 2021; Meincke et al., 2025）を参照。

## すべての抜け穴を明示的に塞ぐ

ルールを述べるだけでなく、具体的な回避策を禁止する:

<Bad>
```markdown
テストの前にコードを書いた? 削除せよ。
```
</Bad>

<Good>
```markdown
テストの前にコードを書いた? 削除せよ。最初からやり直す。

**例外なし:**
- 「参考資料」として残さない
- テストを書きながら「適応」しない
- それを見ない
- 削除は削除を意味する
```
</Good>

## 「精神 vs 文言」の議論に対処する

基本原則を早い段階で追加する:

```markdown
**ルールの文言に違反することは、ルールの精神に違反することである。**
```

これにより「精神に従っている」という合理化のクラス全体を遮断できる。

## 合理化テーブルを構築する

ベースラインテストから合理化を記録する。エージェントが使うすべての言い訳をテーブルに入れる:

```markdown
| 言い訳 | 現実 |
|--------|------|
| 「テストするには単純すぎる」 | 単純なコードも壊れる。テストには30秒しかかからない。 |
| 「後でテストする」 | すぐに通るテストは何も証明しない。 |
| 「テストを後から書いても同じ目的を達成する」 | テスト後 = 「これは何をするか?」 テスト先 = 「これは何をすべきか?」 |
```

## 危険信号リストを作成する

エージェントが合理化しているときに自己チェックしやすくする:

```markdown
## 危険信号 - 停止してやり直す

- テストの前にコードを書いた
- 「手動でテスト済み」
- 「テストを後から書いても同じ目的」
- 「精神であって儀式ではない」
- 「これは違う、なぜなら...」

**これらすべての意味: コードを削除せよ。TDDでやり直せ。**
```

## 違反症状のCSOを更新する

descriptionに追加: ルール違反しそうなときの症状:

```yaml
description: use when implementing any feature or bugfix, before writing implementation code
```
