# スキルのテスト方法論

## すべてのスキルタイプのテスト

異なるスキルタイプには異なるテストアプローチが必要:

### 規律強制スキル（ルール/要件）

**例:** TDD、verification-before-completion、designing-before-coding

**テスト方法:**
- 学術的な質問: ルールを理解しているか?
- プレッシャーシナリオ: ストレス下で準拠するか?
- 複数のプレッシャーの組み合わせ: 時間 + サンクコスト + 疲労
- 合理化を特定し、明示的な対策を追加する

**成功基準:** エージェントが最大のプレッシャー下でルールに従う

### テクニックスキル（ハウツーガイド）

**例:** condition-based-waiting、root-cause-tracing、defensive-programming

**テスト方法:**
- 適用シナリオ: テクニックを正しく適用できるか?
- バリエーションシナリオ: エッジケースを処理できるか?
- 情報欠如テスト: 指示に隙がないか?

**成功基準:** エージェントが新しいシナリオにテクニックを正しく適用できる

### パターンスキル（メンタルモデル）

**例:** reducing-complexity、information-hiding concepts

**テスト方法:**
- 認識シナリオ: パターンが適用されるときに認識できるか?
- 適用シナリオ: メンタルモデルを使えるか?
- 反例: いつ適用しないかを知っているか?

**成功基準:** エージェントがパターンをいつ/どのように適用するか正しく判断できる

### リファレンススキル（ドキュメント/API）

**例:** APIドキュメント、コマンドリファレンス、ライブラリガイド

**テスト方法:**
- 検索シナリオ: 正しい情報を見つけられるか?
- 適用シナリオ: 見つけた情報を正しく使えるか?
- ギャップテスト: 一般的なユースケースがカバーされているか?

**成功基準:** エージェントがリファレンス情報を見つけて正しく適用できる

## テストをスキップする際のよくある合理化

| 言い訳 | 現実 |
|--------|------|
| 「スキルは明らかに明確」 | あなたにとって明確 ≠ 他のエージェントにとって明確。テストせよ。 |
| 「単なるリファレンス」 | リファレンスにもギャップや不明確な箇所がある。検索をテストせよ。 |
| 「テストは過剰」 | テストされていないスキルには問題がある。常に。15分のテストで何時間も節約。 |
| 「問題が出たらテストする」 | 問題 = エージェントがスキルを使えない。デプロイ前にテストせよ。 |
| 「テストは面倒」 | テストは本番で壊れたスキルをデバッグするより面倒ではない。 |
| 「良いものだと確信している」 | 過信は問題を保証する。それでもテストせよ。 |
| 「学術的レビューで十分」 | 読む ≠ 使う。適用シナリオをテストせよ。 |
| 「テストする時間がない」 | テストされていないスキルをデプロイすると、後で修正するのにもっと時間を浪費する。 |

**これらすべての意味: デプロイ前にテストせよ。例外なし。**

## スキルのためのRED-GREEN-REFACTOR

TDDサイクルに従う:

### RED: 失敗するテストを書く（ベースライン）

スキルなしでサブエージェントにプレッシャーシナリオを実行させる。正確な動作を記録する:
- どのような選択をしたか?
- どのような合理化を使ったか（原文のまま）?
- どのプレッシャーが違反を引き起こしたか?

これが「テストの失敗を見る」こと - スキルを書く前に、エージェントが自然に何をするかを見なければならない。

### GREEN: 最小限のスキルを書く

特定の合理化に対処するスキルを書く。仮想的なケースのための追加コンテンツは加えない。

同じシナリオをスキルありで実行する。エージェントが準拠するようになるべきである。

### REFACTOR: 抜け穴を塞ぐ

エージェントが新しい合理化を見つけた? 明示的な対策を追加する。防弾になるまで再テストする。

**テスト方法論:** プレッシャーシナリオの書き方、プレッシャーの種類（時間、サンクコスト、権威、疲労）、体系的な穴の塞ぎ方、メタテスト技法については testing-skills-with-subagents.md（同ディレクトリ内）を参照。
