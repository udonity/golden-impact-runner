# 開発ブランチの完了

## 概要

明確な選択肢を提示し、選択されたワークフローを処理することで、開発作業の完了をガイドする。

**基本原則:** テスト検証 → 選択肢提示 → 選択実行 → クリーンアップ。

**開始時のアナウンス:** 「finishing-a-development-branchスキルを使用してこの作業を完了します。」

## プロセス

### ステップ1: テストの検証

**選択肢を提示する前に、テストが通ることを確認する:**

```bash
# プロジェクトのテストスイートを実行
npm test / cargo test / pytest / go test ./...
```

**テストが失敗した場合:**
```
テスト失敗（<N>件の失敗）。完了前に修正が必要です:

[失敗内容を表示]

テストが通るまでマージ/PRに進めません。
```

停止する。ステップ2に進まない。

**テストが通った場合:** ステップ2に進む。

### ステップ2: ベースブランチの特定

```bash
# 一般的なベースブランチを試す
git merge-base HEAD main 2>/dev/null || git merge-base HEAD master 2>/dev/null
```

または確認する: 「このブランチはmainから分岐しています - 合っていますか？」

### ステップ3: 選択肢の提示

以下の4つの選択肢を正確に提示する:

```
実装が完了しました。どうしますか？

1. ローカルで<base-branch>にマージする
2. プッシュしてPull Requestを作成する
3. ブランチをそのまま残す（後で自分で対応する）
4. この作業を破棄する

どの選択肢にしますか？
```

**説明を追加しない** - 選択肢を簡潔に保つ。

### ステップ4: 選択の実行

#### 選択肢1: ローカルマージ

```bash
# ベースブランチに切り替え
git checkout <base-branch>

# 最新を取得
git pull

# フィーチャーブランチをマージ
git merge <feature-branch>

# マージ結果のテストを検証
<test command>

# テストが通った場合
git branch -d <feature-branch>
```

次に: ワークツリーのクリーンアップ（ステップ5）

#### 選択肢2: プッシュしてPR作成

```bash
# ブランチをプッシュ
git push -u origin <feature-branch>

# PRを作成
gh pr create --title "<title>" --body "$(cat <<'EOF'
## 概要
<変更内容の2-3項目の箇条書き>

## テスト計画
- [ ] <検証手順>
EOF
)"
```

次に: ワークツリーのクリーンアップ（ステップ5）

#### 選択肢3: そのまま残す

報告: 「ブランチ<name>をそのまま残します。ワークツリーは<path>に保持されています。」

**ワークツリーをクリーンアップしない。**

#### 選択肢4: 破棄

**まず確認する:**
```
以下が永久に削除されます:
- ブランチ <name>
- すべてのコミット: <commit-list>
- ワークツリー: <path>

確認するには「discard」と入力してください。
```

正確な確認を待つ。

確認された場合:
```bash
git checkout <base-branch>
git branch -D <feature-branch>
```

次に: ワークツリーのクリーンアップ（ステップ5）

### ステップ5: ワークツリーのクリーンアップ

**選択肢1、2、4の場合:**

ワークツリー内にいるか確認する:
```bash
git worktree list | grep $(git branch --show-current)
```

該当する場合:
```bash
git worktree remove <worktree-path>
```

**選択肢3の場合:** ワークツリーを保持する。

## クイックリファレンス

| 選択肢 | マージ | プッシュ | ワークツリー保持 | ブランチ削除 |
|--------|--------|----------|------------------|-------------|
| 1. ローカルマージ | ○ | - | - | ○ |
| 2. PR作成 | - | ○ | ○ | - |
| 3. そのまま残す | - | - | ○ | - |
| 4. 破棄 | - | - | - | ○（強制） |

## よくある間違い

**テスト検証のスキップ**
- **問題:** 壊れたコードをマージ、失敗するPRを作成
- **対策:** 選択肢を提示する前に必ずテストを検証する

**オープンエンドな質問**
- **問題:** 「次に何をすべきですか？」→ 曖昧
- **対策:** 正確に4つの構造化された選択肢を提示する

**ワークツリーの自動クリーンアップ**
- **問題:** 必要な場合にワークツリーを削除してしまう（選択肢2、3）
- **対策:** 選択肢1と4の場合のみクリーンアップする

**破棄時の確認なし**
- **問題:** 誤って作業を削除する
- **対策:** 「discard」の入力による確認を必須にする

## 危険信号

**絶対にしないこと:**
- テストが失敗した状態で進める
- マージ結果のテスト検証なしにマージする
- 確認なしに作業を削除する
- 明示的な要求なしにforce-pushする

**常に行うこと:**
- 選択肢を提示する前にテストを検証する
- 正確に4つの選択肢を提示する
- 選択肢4では入力による確認を得る
- 選択肢1と4の場合のみワークツリーをクリーンアップする
